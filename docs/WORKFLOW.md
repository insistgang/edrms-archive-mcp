# 开发实施流程

## 项目边界

交付对象是独立的MCP适配服务。客户保留原有档案系统、模型和问答界面；首期原生接口复用，不默认新建MySQL/MinIO/向量库，不直接修改原系统索引、配置或数据。

## 已进行的开发轨迹

1. 资料核对：梳理需求、PPT、会议、API和原型，区分材料提出/实测/建议/待确认。
2. 数据模型：案卷→文件→原文，保留门类、文件、原文、下载版本ID各自语义。
3. 工具实现：四工具、标准MCP与HTTP JSON兼容，真实用户身份透传，失败不降级演示数据。
4. 原文链路：原文列表→关联校验→下载→内存解析→片段和来源；有界ZIP、OOXML和不支持格式错误。
5. 测试审查：单元/HTTP/模拟模型闭环与授权实机样本回归；三轮review修复N+1、匿名查询、验收假通过、上下文JSON、OOXML安全等问题。
6. 接入补齐：MCPClient和命令行模型入口，EDRMSToken与模型密钥隔离。
7. 交付跟踪：代码/测试/脱敏状态入Git；原始资料、凭据和导出数据不入Git。

## 每个新需求的闭环

1. 使用“功能需求”Issue模板登记原始诉求、角色、范围、样本、验收标准、风险与依赖；不能把客户口头描述自动写成已承诺。
2. 澄清身份权限和现有接口；涉及客户系统写入、生产部署、外发数据或新组件时先取得明确批准。
3. 用feature/fix分支实施；避免把真实档案、内网地址和凭据写进测试。
4. 回归：`python3 -m unittest discover -p 'test_*.py'`、`python3 acceptance_test.py`；相关实机场景只在授权环境执行。
5. Pull Request附需求Issue、变更范围、测试命令/结果、未验证点、权限影响和回退方法。
6. Review至少覆盖功能正确、权限/数据边界、异常/兼容。测试失败或仍缺依赖不关闭验收Issue。
7. 更新CHANGELOG、STATUS和README；客户确认实际场景后关闭Issue。现场证据保存于客户批准环境，GitHub仅留脱敏结论。

## 五个阶段门槛

| 阶段 | 输入 | 产出 | 进入下一阶段条件 |
|---|---|---|---|
| 现场确认 | 字段/门类/认证/接口/样本/环境 | 确认清单、权限矩阵、验收约定 | 真实身份及样本可用 |
| 单条业务闭环 | 有权限文件及原文 | 检索→详情→原文→来源证据 | 普通业务身份及真实正文一致 |
| 四类扩展 | 各门类字典/立卷/多原文 | 字段映射、关联和格式记录 | 各类样本人工核对通过 |
| 权限与性能 | A/B用户、预期矩阵、阈值 | 可复现权限/并发报告 | 真实客户模型、安全和性能签认 |
| 可选语义增强 | 原生检索不足证据及批准资源 | 向量/OCR/同步对照评测 | 权限及效果目标达成 |

## 后续维护方式

每次客户带来新需求时，在同一仓库创建/更新Issue，并同步相关代码、测试、文档和CHANGELOG。不会自动感知客户聊天或持续监控需求；需要用户把新需求交给助手或登记在仓库。发布、推送及部署保持用户明确授权，生产动作不因Issue存在而自动执行。
